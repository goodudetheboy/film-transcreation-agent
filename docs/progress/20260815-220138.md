# 2026-08-15 22:01 — Settings modal, remembered passcode

## What changed

- Converted the settings dropdown into a real modal, per user request: full-viewport
  dark backdrop, centered panel, "×" close button, click-outside-to-close, and
  Escape-to-close. Built test-first — `HeaderSettings.test.tsx` now covers backdrop
  click, clicking inside the modal (should NOT close), and Escape. Same
  `testMode`/`onTestModeChange` props as before, so `App.tsx` needed no changes.
- Added remembered-passcode persistence to `PasscodeGate`, per user request: on a
  successful manual unlock, the passcode is saved to
  `localStorage["film-transcreation-agent:passcode"]`. On mount, if a saved passcode
  exists, it's automatically re-verified against the backend (never trusted blindly
  — the backend passcode could have changed) and either auto-unlocks silently or,
  if stale/wrong, clears the bad value and falls back to the normal empty form. Five
  new test cases cover: saves on success, doesn't auto-check when nothing is saved,
  auto-unlocks from a valid saved value, clears + shows the form on a stale value.
  Verified live: unlocked once, reloaded the page, landed straight on the main form
  with no passcode prompt.

## Debugging note (not a code change)

- Hit real dev-environment flakiness while verifying live: multiple overlapping
  `npm run dev:backend`/`dev:frontend` process trees ended up running
  simultaneously across several verification passes, causing intermittent
  `EADDRINUSE` crashes and connection-refused errors that looked like application
  bugs but weren't. Root cause: repeated manual dev-server boots during this
  session without confirming the previous tree was fully dead first. Resolved by
  listing all `node.exe` processes matching the project path and tree-killing all
  of them before each restart. Not a code issue — `scripts/dev.sh`'s own cleanup
  trap (already using `taskkill /T`, see the 2026-08-15 20:24 entry) is the
  intended defense against exactly this when using the one-click script instead of
  manual `npm run dev:*` invocations in separate terminals.
- User reported hitting a similar-sounding failure locally after running
  `gcloud auth application-default login` and then the startup script — likely the
  same class of issue (leftover process holding the port) rather than an auth
  problem, but unconfirmed pending their exact error output.
