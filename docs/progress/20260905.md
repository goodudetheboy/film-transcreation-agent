## 20:00 — Phase 1 implemented and verified

Root-caused and fixed all three Phase 1 bugs from an approved plan.

**1. Discovery status stuck on "Working" until reload**
[DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx):
the effect that opens each run's resumable `streamDiscoveryJob` connection was
keyed on `activeSession.turns.length`, so sending a chat message while a job
was still running tore down its live subscription (via a `cancelled`-flag
cleanup) before the terminal `done` event arrived — the subscription was
already keyed as "existing" so it never got re-opened. Replaced the
cleanup-based dedup with a `subscribedJobIdsRef` that's never torn down by an
unrelated re-render, only reset when `filmId` changes. Verified live: kicked
off a run, sent a chat message mid-run, confirmed (via temporary console
instrumentation, since removed) the terminal event now reaches `setJobDetails`
and the run card flips to "done" with no reload.

**2. Default research kickoff invisible**
[NewProjectModal.tsx](../../frontend/src/components/NewProjectModal.tsx):
`handleFinish` called `streamResearchRun` with a no-op event handler and never
created a `ChatSession` or logged the run into one — exactly the
`ResearchChatPanel.tsx` `KickoffForm.handleSubmit` pattern, just not applied
here. Fixed by mirroring that pattern (`createChatSession` → `streamResearchRun`
→ `logResearchRun` on the first `progress` event). Verified live end-to-end:
created a project with the checkbox on, confirmed `POST chat-sessions` →
`POST research-runs` → `POST chat-sessions/:id/research-runs` all fire, and
after a reload the project's Agents panel shows the session with a "Custom
research run — done" card. One residual nuance found and left as-is (small,
same flavor as bug 1 but out of this plan's scope): opening the session in the
same tick it's created can briefly show the empty kickoff form instead of the
run card, because `ProjectPanel`'s one-shot `listChatSessions` on mount can
race the fire-and-forget `createChatSession`/`logResearchRun` chain; a reopen
or reload always shows it correctly. Worth a follow-up if it bothers the user
in practice.

**3. Agent context-staleness cluster** — new
[ADR-0027](../adr/0027-chat-agent-context-freshness.md) written, closing the
risk ADR-0025 had flagged:
- 3a (can't resolve "row 04:08–04:10"): `buildDetailsContext` in
  [discoveryChatAgent.ts](../../backend/src/services/discoveryChatAgent.ts)
  now includes each row's `mm:ss` timestamp range — no new tool needed.
- 3b (deleted rubric "still exists"): added
  `ProjectItemStore.removeRubricScore` (Firestore + in-memory), wired into
  `DELETE /api/projects/:id/rubrics/:rubricId` — actually prunes the orphaned
  score and recomputes `importanceScore`, rather than filtering it at read
  time. Verified live against the real dev backend: patched a score to 8,
  deleted its rubric, confirmed the score entry is gone from
  `GET /items` and `importanceScore` recomputed off the remaining rubrics.
- 3c (can't edit a custom column): `DetailRowsStore.updateRow`'s merge now
  deep-merges `values.custom` instead of replacing it wholesale (a one-field
  patch was silently wiping sibling custom columns);
  `edit_detail_row`'s tool now accepts any real column key (validated against
  `listColumns`), and `buildDetailsContext` surfaces column name/description/
  current value so the model knows custom columns exist at all. Scoped to the
  Discovery chat agent only, per ADR-0027 — the research chat agent's tools
  weren't reported as having this gap.
- Note: 3a/3c's *model-reasoning* behavior (does Gemini actually pick the
  right row/field given the new context) could only be verified via unit
  tests with a scripted fake model — this repo's test mode runs a canned
  mock agent that ignores the user's actual text, so browser verification
  couldn't exercise real Gemini decision-making. The mechanical pieces
  (context content, tool validation, store merge) were verified live via a
  passing new unit test suite and, for 3b, a live API call against the real
  dev backend.

Decisions:
- No new ADR for fixes 1 and 2 — pure bug fixes, no architectural change.
- ADR-0027 added for fix 3, since it closes a previously-documented
  architectural risk (see ADR-0025).
