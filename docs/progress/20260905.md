# 2026-09-05

## Triage of a large user-feedback batch (~22 items)

User dropped a large, unstructured batch of feedback (bugs, UX polish, and
new-feature asks). Sifted it into phases and wrote it up as
[docs/backlog.md](../backlog.md), added a pointer to it from
[docs/README.md](../README.md).

Grouping logic: real bugs first (especially ones eroding trust in the
agent), then cheap independent wins, then two rounds of chat/table UX rework,
then anything that needs the user's own mockups (project-detail redesign,
rubrics editor + Miro reference) or an open design discussion (backfill-on-
existing-rows flow, drag-and-drop into chat, live-edit visual flair) before
any code gets written.

One finding worth flagging: three separate feedback items (agent edits the
wrong row, agent insists a deleted rubric still exists, agent can't touch a
custom "Food" field) are the same root cause, not three bugs — and it's a
risk [ADR-0025](../adr/0025-projects-firestore-pipeline-and-tool-calling-research-chat.md)
already named explicitly in its Consequences section ("a chat session's tool
calls are only ever as good as whatever item the frontend says is
'currently open'... No cross-check against the conversation's own text
exists to catch that"). Folded into Phase 1 as one cluster rather than
three separate fixes; likely needs an ADR update once the fix is designed,
not just a patch.

No code changed this session. Next: plan and implement Phase 1 (status
not refreshing after a Discovery run, default research-kickoff regression,
the agent-context-staleness cluster above).

## 20:00 — Phase 1 implemented and verified

Root-caused and fixed all three Phase 1 bugs from an approved plan.

**1. Discovery status stuck on "Working" until reload**
[DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx):
the effect that opens each run's resumable `streamDiscoveryJob` connection was
keyed on `activeSession.turns.length`, so sending a chat message while a job
was still running tore down its live subscription (via a `cancelled`-flag
cleanup) before the terminal `done` event arrived — the subscription was
already keyed as "existing" so it never got re-opened. Replaced the
cleanup-based dedup with a `subscribedJobIdsRef` that's never torn down by an
unrelated re-render, only reset when `filmId` changes. Verified live: kicked
off a run, sent a chat message mid-run, confirmed (via temporary console
instrumentation, since removed) the terminal event now reaches `setJobDetails`
and the run card flips to "done" with no reload.

**2. Default research kickoff invisible**
[NewProjectModal.tsx](../../frontend/src/components/NewProjectModal.tsx):
`handleFinish` called `streamResearchRun` with a no-op event handler and never
created a `ChatSession` or logged the run into one — exactly the
`ResearchChatPanel.tsx` `KickoffForm.handleSubmit` pattern, just not applied
here. Fixed by mirroring that pattern (`createChatSession` → `streamResearchRun`
→ `logResearchRun` on the first `progress` event). Verified live end-to-end:
created a project with the checkbox on, confirmed `POST chat-sessions` →
`POST research-runs` → `POST chat-sessions/:id/research-runs` all fire, and
after a reload the project's Agents panel shows the session with a "Custom
research run — done" card. One residual nuance found and left as-is (small,
same flavor as bug 1 but out of this plan's scope): opening the session in the
same tick it's created can briefly show the empty kickoff form instead of the
run card, because `ProjectPanel`'s one-shot `listChatSessions` on mount can
race the fire-and-forget `createChatSession`/`logResearchRun` chain; a reopen
or reload always shows it correctly. Worth a follow-up if it bothers the user
in practice.

**3. Agent context-staleness cluster** — new
[ADR-0027](../adr/0027-chat-agent-context-freshness.md) written, closing the
risk ADR-0025 had flagged:
- 3a (can't resolve "row 04:08–04:10"): `buildDetailsContext` in
  [discoveryChatAgent.ts](../../backend/src/services/discoveryChatAgent.ts)
  now includes each row's `mm:ss` timestamp range — no new tool needed.
- 3b (deleted rubric "still exists"): added
  `ProjectItemStore.removeRubricScore` (Firestore + in-memory), wired into
  `DELETE /api/projects/:id/rubrics/:rubricId` — actually prunes the orphaned
  score and recomputes `importanceScore`, rather than filtering it at read
  time. Verified live against the real dev backend: patched a score to 8,
  deleted its rubric, confirmed the score entry is gone from
  `GET /items` and `importanceScore` recomputed off the remaining rubrics.
- 3c (can't edit a custom column): `DetailRowsStore.updateRow`'s merge now
  deep-merges `values.custom` instead of replacing it wholesale (a one-field
  patch was silently wiping sibling custom columns);
  `edit_detail_row`'s tool now accepts any real column key (validated against
  `listColumns`), and `buildDetailsContext` surfaces column name/description/
  current value so the model knows custom columns exist at all. Scoped to the
  Discovery chat agent only, per ADR-0027 — the research chat agent's tools
  weren't reported as having this gap.
- Note: 3a/3c's *model-reasoning* behavior (does Gemini actually pick the
  right row/field given the new context) could only be verified via unit
  tests with a scripted fake model — this repo's test mode runs a canned
  mock agent that ignores the user's actual text, so browser verification
  couldn't exercise real Gemini decision-making. The mechanical pieces
  (context content, tool validation, store merge) were verified live via a
  passing new unit test suite and, for 3b, a live API call against the real
  dev backend.

Decisions:
- No new ADR for fixes 1 and 2 — pure bug fixes, no architectural change.
- ADR-0027 added for fix 3, since it closes a previously-documented
  architectural risk (see ADR-0025).

Verified: `npm run test` — 61 frontend + 228 backend (4 new: a
`detailRowsStore` custom-merge test, two `discoveryChatAgent` tests for
timestamps/custom-field editing, one `projectItemStore` test for
`removeRubricScore`) + 10 integration, all passing. Both `tsc` checks clean
(`-p tsconfig.json` for backend, `-p tsconfig.app.json` for frontend per
[[feedback-tsc-invocation]]). Live-walked all three fixes via the dev servers
in the Browser pane as described above; a leftover test project ("Germany",
under "Your Body Count Is What?") and a couple of scratch rubrics from this
verification pass are still in the dev Firestore project — the app has no
project-delete API route to clean it up programmatically, so it's left for
the user to delete via the UI if it's in the way (it doubles as a working
demo of fix 2).

## 20:35 — Phase 2 implemented and verified

Planned (via a written plan approved before coding) and implemented all four Phase 2
backlog items.

**1. Renameable agent/session title.** `ChatSession`/`DiscoveryAgentSession` already had
a `name` field and store-layer `updateSession` patching, and the name was already shown
in the session library list — but the open-chat view had no title bar at all, and no
PATCH route existed. Added `PATCH /api/projects/:id/chat-sessions/:sessionId` and
`PATCH /api/films/:id/discovery-agents/:agentId`
([projectChat.ts](../../backend/src/routes/projectChat.ts),
[discoveryChat.ts](../../backend/src/routes/discoveryChat.ts)), matching frontend client
functions, and a new shared
[EditableTitle.tsx](../../frontend/src/components/EditableTitle.tsx) component (pencil
icon → inline input, Enter/blur saves, Escape cancels) wired into both
[DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx) and
[ResearchChatPanel.tsx](../../frontend/src/components/ResearchChatPanel.tsx). Verified
live: renamed a Research session and a Discovery agent, reloaded, both names persisted.

**2. Project-creation table: select-all + all columns.**
[DetailRowPicker.tsx](../../frontend/src/components/DetailRowPicker.tsx) hardcoded 3
columns and had no select-all, while `DetailsTable.tsx` already had the full
built-in-plus-custom column model. Extended `DetailRowPicker` to take `columns` and
`onToggleAll` props (both optional, so existing callers keep working unchanged) and wired
them into both `NewProjectModal.tsx` (the target of this item) and `ProjectPanel.tsx`'s
"+ Manually add details" modal, since it's the same shared component. Verified live: a
freshly-added custom "Food" column and the built-in Gesture/Notes columns all render in
the new-project wizard's table, and the select-all checkbox correctly selects/deselects
all rows and updates the "Next (N selected)" count.

**3. Default rubrics generator.** `DEFAULT_RUBRICS`
([defaultRubrics.ts](../../backend/src/config/defaultRubrics.ts)) already existed
server-side (6 rubrics, all `weight: 3` — already equal-weighted) but was only used as a
silent fallback on project creation with zero rubrics; there was no way to see or insert
it from the UI. Added a small `GET /api/default-rubrics` route
([config.ts](../../backend/src/routes/config.ts), same one-purpose-file precedent as
`health.ts`) and a "Use default rubrics" button in
[RubricsEditor.tsx](../../frontend/src/components/RubricsEditor.tsx), append-only (never
touches existing rows) — wired to append to local draft state in the new-project wizard
and to actually persist via `createRubric` in an existing project's Rubrics tab. Verified
live in both contexts: wizard's Rubrics step and an existing project's Rubrics tab.

**4. Relabel "Verdict"/"Action".** Two-line change in
[ProjectPanel.tsx](../../frontend/src/components/ProjectPanel.tsx) — confirmed via
research that neither word is used as a backend/type identifier anywhere (the AI
judgment is `shouldTranscreate`/`summary`, the user's decision is `ProjectItemAction`),
so this was purely cosmetic. Verified live: Items tab now shows "AI ASSESSMENT" /
"YOUR VERDICT".

Decisions:
- No new ADR — all four items are additive UI/route changes with no architectural
  implications.
- `DraftRubric` (the wizard's local rubric shape) still has no `trendEligible` field, so
  the one default with `trendEligible: true` ("Slang / meme reference") gets created as
  `false` when added via the wizard's draft state — a pre-existing gap (manually-typed
  wizard rubrics already couldn't set this field either), not introduced by this change,
  left as-is.

## 23:10 — Phase 3 implemented and verified

Planned (via a written plan approved before coding) and implemented all four Phase 3
"chat UX" backlog items, applied identically to both
[ResearchChatPanel.tsx](../../frontend/src/components/ResearchChatPanel.tsx) and
[DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx).

**1. Stop-generation button — true backend cancellation, not just client-side.**
User decided against a client-only stop (backend would keep running tool calls
silently after the click). Confirmed `@google/genai`'s `generateContentStream`
accepts `config.abortSignal` (`node_modules/@google/genai/dist/genai.d.ts`), and this repo
already had the exact precedent for detecting a client disconnect —
`req.on('close', unsubscribe)` in `routes/films.ts`/`routes/projects.ts`'s resumable
SSE streams. Added `signal?: AbortSignal` to both chat agents' `RunTurnInput`
([researchChatAgent.ts](../../backend/src/services/researchChatAgent.ts),
[discoveryChatAgent.ts](../../backend/src/services/discoveryChatAgent.ts)), wired
into `generateContentStream`'s `abortSignal` and (research only) the `search_web`
tool's raw fetch; a new `'stopped'` event type distinguishes a deliberate stop from
a real error. Both `.../messages` routes now create an `AbortController`, abort it on
`req.on('close')`, and pass its signal through. Frontend: `ApiClientOptions` gained
an optional `signal`; both chat API clients pass it into `fetch` and treat a thrown
`AbortError` (from either the initial fetch or the SSE read loop) as a quiet no-op,
not an error banner. Each panel keeps an `abortControllerRef`, renders a "Stop"
button in place of "Send" while `sending`, and calls `.abort()` on click. Verified:
new backend unit tests (pre-aborted signal → no model call, `{type:'stopped'}` only;
stream rejecting with an `AbortError` → `'stopped'`, not `'error'`) plus a live check
in the Browser pane that "Stop" appears during `sending` and the turn ends cleanly
(mock agents run synchronously, so true mid-stream cancellation is what the unit
tests cover — the mock has nothing slow enough to interrupt live).

**2. User's own bubble appears immediately.** Both panels now set a
`pendingUserText` state right before the send call and render it as a
`chat-bubble--user` div immediately after the persisted turns, clearing it once the
post-send session refetch replaces it with the real persisted turn. Verified live in
both panels: the typed message appears in the thread the instant Send is clicked,
well before the mock agent's reply arrives.

**3. Markdown rendering in chat bubbles.** Added `react-markdown` + `remark-gfm` as
frontend deps (user's choice over a hand-rolled parser). New
[ChatMarkdown.tsx](../../frontend/src/components/ChatMarkdown.tsx) wraps
`ReactMarkdown` with `remark-gfm` and an external-link-safe `a` renderer; no
`rehype-raw`, so the model's raw HTML output stays escaped rather than executed.
Applied only to model/system bubbles, not user bubbles (typed text, not
agent-generated markdown) — added matching CSS in
[index.css](../../frontend/src/index.css) to reset `white-space` and collapse block
margins inside `.chat-bubble--model`/`--system`. The mock chat agents' canned replies
contain no markdown syntax, so this couldn't be demoed live through the app; verified
instead via a throwaway component-render test (bold/list/link/inline-code all render
as real elements, not literal `**`/`-` — written, run once, then deleted, not part of
the permanent suite) and confirmed no regressions via the full `npm run test`.

**4. Kickoff form moves to a modal.** Extracted the backdrop/header/close chrome
shared by every existing modal in this app into a new
[Modal.tsx](../../frontend/src/components/Modal.tsx) (in-scope cleanup — the exact
chrome was about to be copy-pasted a third time); refactored
[ConfirmModal.tsx](../../frontend/src/components/ConfirmModal.tsx) to use it. Both
panels' inline `KickoffForm` (previously auto-shown when a session had zero turns,
or toggled inline via a button) now only renders inside `<Modal className="kickoff-
modal">`; an empty session instead shows a plain placeholder + a "Kick off a
[research run/agentic discovery]" button that opens the modal. Removed the
now-redundant title paragraph each `KickoffForm` used to render inside itself (the
Modal's header supplies it). Verified live: clicking the button opens a centered
modal (confirmed via `getBoundingClientRect` in the Browser pane, since the pane's
own screenshot scaling made a visual check misleading) with no form ever appearing
inline in the thread, for both a brand-new empty session and the "kick off another"
button on an existing one.

Decisions:
- No new ADR — all four items are additive UI/streaming-plumbing changes with no
  architectural implications beyond what ADR-0025 already covers for chat.
- Reused the existing `Modal` extraction for `ConfirmModal` rather than leaving two
  near-identical copies of the backdrop/header chrome now that a second consumer
  (the kickoff form) needed it — `NewProjectModal`/`DetailsTable`'s inline modals
  left as-is (out of scope, bigger components).

Verified: `npm run test` — 238 backend (4 new: 2 stop/abort tests each in
`researchChatAgent.test.ts`/`discoveryChatAgent.test.ts`), 61 frontend, 10
integration, all passing. Both `tsc` checks clean. Live-walked all four items via the
dev servers in the Browser pane as described above.
