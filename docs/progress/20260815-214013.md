# 2026-08-15 21:40 — Fix passcode UX + dotenv bug, film-editor redesign

## What changed

- **Fixed a real production bug**: `dotenv` was a listed dependency but never
  actually imported anywhere — `backend/.env` was silently ignored at runtime, so
  `SHARED_PASSCODE` (and every other env var) always fell back to its hardcoded
  default (`dev-passcode`), regardless of what `.env` said. Root-caused by testing
  the app in a real browser after the redesign (user reported a 401 they couldn't
  explain from `backend/.env` clearly saying `SHARED_PASSCODE=test`) — direct curl
  against the running server confirmed the deployed config didn't match the file on
  disk. Fixed with one line: `import 'dotenv/config'` at the top of
  `backend/src/server.ts`. This bug existed since the original scaffold; none of the
  unit/integration tests caught it because they all inject config directly into
  `createApp()`, bypassing `loadConfig()`'s env-reading path entirely — the missing
  link was purely "get real config into the process at boot," which isn't something
  the existing test architecture was ever positioned to catch.
- **Fixed a real UX bug, flagged by the user mid-session**: `PasscodeGate` accepted
  any non-empty string and showed the main UI immediately — the actual passcode
  check only ever happened when hitting Analyze, deep in the flow. Added
  `POST /api/verify-passcode` (backend, guarded by the same `passcodeMiddleware` as
  everything else — see `docs/adr/0005`'s new "Update" section) and wired the
  frontend's `PasscodeGate` to call it before ever calling `onUnlock`, showing an
  inline error on the gate itself if wrong.
- Added `ErrorBanner` component — a sticky, full-width red bar at the very top of
  the page showing the exact error (status code + backend detail, e.g.
  `"request failed with status 401: invalid passcode"`) with a "Try again" button.
  Requested by the user specifically to make debugging/reporting errors easier.
  Refactored `apiClient.ts`'s error-detail extraction (parse JSON `{error: "..."}"`
  body, fall back to raw text, fall back to status-only) into a shared
  `describeError()` helper used by both `streamAnalyze` and the new
  `verifyPasscode`.
- Since the passcode is now verified before the user ever reaches the main form, an
  error during Analyze is no longer a passcode problem — changed "Try again" to just
  reset the results store and stay on the form, instead of bouncing back to the
  passcode gate.
- Full visual redesign per user request ("film editor sort of thing," sharp corners
  instead of rounded): rewrote `frontend/src/index.css` from the leftover Vite
  template into a deliberate dark, single-theme design system (CSS custom
  properties for a near-black background, amber accent, monospace throughout,
  `border-radius: 0` everywhere). Two-panel "editing bay" layout (script/country on
  the left, flagged-line results as bordered "clip cards" on the right), toolbar-style
  header, locked-terminal-style passcode gate.
- All of this was verified live in a real browser (Claude Browser pane), not just
  via unit tests: booted both dev servers, walked through wrong-passcode →
  inline-error, correct-passcode → main UI, submit → real ADC error surfaced
  correctly in the top banner, Try Again → clean reset. Screenshots confirmed the
  redesign renders as intended and caught one bug live (password input hadn't
  picked up the dark input styling — CSS selector only covered `type="text"`, fixed).

## Decisions made (and where they're recorded)

- `docs/adr/0005-backend-responsibilities.md` — added an "Update" section
  documenting `POST /api/verify-passcode`, rather than a new ADR number, since it's
