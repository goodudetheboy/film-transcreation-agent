# 2026-09-03

## 00:35 — Discovery agent → chat-sidebar redesign

Replaced the Details tab's "Kick off agentic discovery" modal flow
(`AgentKickoffPanel` → `AgentRunningList` → `AgentStatusPanel`) with a
chat-sidebar experience matching the Project tab's research agent pattern
(`ResearchChatPanel`: sparkle toggle, session library, threaded
conversation) — confirmed over two rounds of clarifying questions before
planning (see chat for the full Q&A), then implemented from an approved
plan. This was a real feature build, not a restyle: `DiscoveryJob` (the
actual pass-running job — queueing, the Gemini scan for candidate lines,
streaming status) stays completely untouched; what's new is a chat layer on
top of it, mirroring the Project chat architecture file-for-file.

**Confirmed flow**: one Agent = one persistent thread (`agentNumber`, lining
up with `DiscoveryJob.agentNumber`). A library lists past Agents; "+ New
agent" starts a fresh one and shows the kickoff form (label, special
instruction, target columns — same fields `AgentKickoffPanel` had) inline in
the empty thread, no modal. Submitting logs "Run #1" as a rich card in the
conversation. A "Kick off another pass" button inside the thread reopens the
same form for Run #2, etc. — still the same Agent. The agent can answer
questions about its runs and, when asked, edit any Detail row's field values
or accept/discard its own candidate rows — applying changes immediately, no
confirm step, same as the research agent's existing `update_rubric_score`
behavior.

**Backend** (new files, mirroring the Project chat stack):
- `filmTypes.ts`: added `DiscoveryAgentSession`/`DiscoveryChatTurn`/
  `DiscoveryChatPart` (the last with a `run: {jobId}` variant beyond what
  `ChatPart` has — a reference to a `DiscoveryJob` pass, rendered inline in
  the thread's timeline alongside chat messages).
- `discoveryChatSessionStore.ts` — copies `chatSessionStore.ts` exactly
  (Firestore + in-memory), `films/{filmId}/discoveryAgents/{agentId}`,
  numbered field is `agentNumber` not `sessionNumber`.
- `discoveryChatAgent.ts` — copies `researchChatAgent.ts`'s
  `runTurn(): AsyncGenerator` + injectable `ChatGenAIClient` pattern
  (reused as-is, not redefined). Three tools, all narrower than research
  chat's set: `edit_detail_row` (subtitleText/segmentDescription/gesture/
  notes, any row in the film — calls the existing
  `DetailRowsStore.updateRow`, no store changes needed), `merge_candidate_row`
  / `discard_candidate_row` (same effect as the existing Add/Delete
  buttons). Persisted turns keep `role: 'system'` run-marker turns for the
  frontend timeline but strip them before sending `contents` to Gemini —
  the model gets the same info via a "THIS AGENT'S RUNS" system-instruction
  block built from `discoveryJobStore` directly.
- `discoveryResultActions.ts` (new) — extracted the merge/discard logic
  that used to live inline in `routes/films.ts`'s two result routes into
  shared `mergeDiscoveryResult`/`discardDiscoveryResult` functions, now used
  by both those routes AND the new chat tools (avoids duplicating the same
  effect in two places) — also now publishes to the existing
  `DiscoveryEventBus` after mutating, so any open run card reflects a
  chat-triggered merge/discard live even from a different origin.
- `mockDiscoveryChatAgent.ts` — mirrors `mockResearchChatAgent.ts`: a canned
  demo that genuinely calls the same `executeTool()` the real agent uses
  (merges the first pending candidate it finds across this agent's runs, or
  falls back to editing the first Detail row's notes if none are pending).
- `routes/discoveryChat.ts` — mirrors `routes/projectChat.ts`
  (create/list/get session, SSE `/messages`), plus one new endpoint with no
  counterpart there: `POST .../runs` — thin, body `{jobId}` of an
  already-created `DiscoveryJob` (via the existing unchanged
  `POST .../discovery-jobs`), just files the `run` reference turn.
- `app.ts` / `server.ts` — wired the new store + real/mock agent through
  `AppDeps` and production Firestore/Gemini config, same pattern as every
  other store here.

**Frontend**:
- `discoveryChatApiClient.ts` (new) — mirrors the project chat API client
  shape; reuses `filmsApiClient.ts`'s existing `createDiscoveryJob`/
  `streamDiscoveryJob`/`mergeDiscoveryResult`/`discardDiscoveryResult`
  unchanged for the actual pass mechanics.
- `filmWorkspaceStore.ts` — removed the flat `jobs`/`jobDetails`/
  `activeJobId` state (no longer needed, that bookkeeping moved into the
  panel itself); added a `discoveryChatSessions`/`activeDiscoveryChatSessionId`
  slice mirroring `projectWorkspaceStore.ts`'s chat slice, with
  `applyDiscoveryChatEvent` reacting to `row_patched`/`row_added` by calling
  the store's existing `updateRow`/`addRow` — so a chat-triggered edit shows
  up live in the Details table itself, not just the chat thread.
- `DiscoveryChatPanel.tsx` (new) — structurally copies `ResearchChatPanel.tsx`
  (library/thread toggle, `.chat-panel*` CSS reused as-is) plus three new
  pieces: `KickoffForm` (the inline pass-config form), `DiscoveryRunCard`
  (today's `AgentStatusPanel` content restyled as an inline card — the panel
  keeps a small `jobDetails` cache populated via `streamDiscoveryJob`, kept
  in sync by both direct button clicks and chat-triggered `row_added`/
  `row_discarded` events), and `DiscoveryToolCallCard` for the edit/merge/
  discard tool-result bubbles.
- `FilmWorkspaceView.tsx` — the Details tab's sparkle button is now a plain
  toggle swapping the left panel between the table and `DiscoveryChatPanel`
  (mirrors how `ProjectPanel` already swaps Items/Rubrics content), instead
  of opening a modal. **Removed the Progress tab entirely** — its sole
  content (`AgentRunningList` + `AgentStatusPanel`) no longer exists, fully
  superseded by the Details tab's new agent view; kept Details/Project only.
- Deleted `AgentKickoffPanel.tsx`, `AgentRunningList.tsx`,
  `AgentStatusPanel.tsx`.

Decisions:
- No ADR — extends the existing chat-agent pattern (ADR 0025) to a second
  domain rather than introducing a new architecture.
- Progress tab removal wasn't explicitly asked for but follows necessarily
  from deleting its only content; flagged to the user in this log rather
  than silently dropped.

Found and fixed along the way (unrelated to this feature, but discovered
because this was the first time `-p tsconfig.app.json` was used instead of
the silently-no-op `-p tsconfig.json`, see memory `feedback-tsc-invocation`):
`useStageDwell.ts`'s `StageDwellController` used constructor parameter-property
shorthand, which `erasableSyntaxOnly: true` doesn't allow — rewritten with
explicit field declarations, same runtime behavior.

Verified: `npm run test` (60 frontend + 221 backend + 9 integration, all
passing — new coverage: `discoveryChatSessionStore.test.ts`,
`discoveryChatAgent.test.ts` covering all three tools plus the
system-turn-stripping behavior, `discoveryChatRoute.test.ts`, and a new
`discoveryChat.integration.test.ts` exercising a real backend end-to-end
with the mock chat agent). Both `tsc` checks clean. Walked the full flow
live via the dev servers (test mode, both themes, and again after
restarting with the new Firestore-backed production wiring): empty library →
new agent → inline kickoff → Run card with candidates → Add button →
discard/merge via chat (tool-result cards render, run card updates live) →
"Kick off another pass" → Run #2 in the same Agent thread → library shows
both this Agent and a second independently-created one, switchable.

## 01:30 — Project tab: "Kick off agentic research" → chat-sidebar (mirror Discovery)

Converted the Project tab's "✨ Kick off agentic research" bulk-run button
(`ResearchKickoffPanel` modal → `streamResearchRun`) to the same
chat-sidebar flow the Discovery agent got earlier today, from an approved
plan (`cosmic-wishing-avalanche.md`). Unlike Discovery, this project already
had a real per-item chat-agent stack (`chatSessionStore.ts` /
`researchChatAgent.ts` / `ResearchChatPanel.tsx`) — confirmed `ChatSession` is
project-scoped only, so the bulk-run flow and the existing per-item chat are
now the *same* session list and the *same* `ResearchChatPanel`, not a
parallel stack. The trickier part: a research run executes synchronously
inline in one request (`routes/projects.ts`, an ADR-0025-flagged deliberate
choice) rather than through a queue like Discovery — didn't touch that
execution model; instead wired up the resumable per-run stream
(`GET .../research-runs/:runId/stream` / `streamResearchRunUpdates()`) that
already existed but had no caller, so the Run card is independent of
whichever request originally kicked the run off (same pattern as
`DiscoveryRunCard`).

**Backend**:
- `projectTypes.ts` / `apiClient.types.ts`: `ChatPart` gained a `run?: {
  runId }` variant and `ChatTurn.role` gained `'system'` — same shape as
  `DiscoveryChatPart`/`DiscoveryChatTurn`. No new session/store type needed
  (unlike Discovery) since `ChatSession` already fit.
- `routes/projects.ts`: the kickoff route's very first SSE event
  (`progress`) now carries `runId` — the one protocol tweak the whole plan
  hinged on, since nothing else exposed the new run's id to a caller that
  isn't reading the full run doc.
- `routes/projectChat.ts`: new thin endpoint mirroring Discovery's
  `.../runs` — `POST .../chat-sessions/:sessionId/research-runs` (body
  `{runId}` of an already-created `ResearchRun`), appends a `role: 'system'`
  run-marker turn.
- `researchChatAgent.ts`: same "strip system turns before sending `contents`
  to Gemini, but keep them in the persisted timeline" convention as
  `discoveryChatAgent.ts`; added a "THIS SESSION'S RUNS" system-instruction
  block (mode/status/batch progress) built by cross-referencing `run` parts
  against `researchRunStore.getRun(...)` — added `researchRunStore` as a new
  required dep. No new tools needed — a bulk run's results land directly in
  `ProjectItem.scores` the same way `update_rubric_score` already writes
  there, so there's no accept/discard review gate to build (unlike
  Discovery's merge/discard).
- `app.ts` / `server.ts`: threaded `researchRunStore` into `projectChatRoute`
  and into `createResearchChatAgent`'s deps.

**Frontend**:
- `projectsApiClient.ts`: added `logResearchRun`. `streamResearchRunUpdates`
  (already exported, previously unused) is now load-bearing.
- `projectWorkspaceStore.ts`: added `upsertChatSession` (mirrors
  `upsertDiscoveryChatSession`) for the "session already exists, just got a
  new run turn appended" case, alongside the existing append-only
  `addChatSession`.
- `ResearchChatPanel.tsx`: added an inline `KickoffForm` (same fields
  `ResearchKickoffPanel` had — need-research vs custom item picker, test
  mode) and a `ResearchRunCard` that subscribes to `streamResearchRunUpdates`
  independently. On submit, the form rides `streamResearchRun`'s connection
  only long enough to read `runId` off the first event, calls
  `logResearchRun`, then closes — the run keeps executing server-side and
  the Run card + a `listItems` re-fetch (triggered on every run_update, so
  the table behind the panel keeps scoring live) take over from the
  resumable stream. The kickoff form auto-shows only for a brand-new
  *project-level* session (no `itemId`); an item-context session gets a
  manual "Kick off a research run" button instead, since jumping into a bulk
  run isn't the obvious default while mid-review on one line. Deleted the
  now-unused `TurnParts` helper component (inlined, matching Discovery's
  per-part rendering so `run` parts can render `ResearchRunCard`).
- `ProjectPanel.tsx`: replaced the `showKickoff`/`ResearchKickoffPanel` modal
  and the big primary button with an `agentsOpen` boolean (persisted to
  `localStorage`, same as `ProjectItemView`'s `chatOpen`) driving a
  `chat-toggle-btn` pill and a sliding panel — new `.project-panel__body` /
  `__main` / `__chat` / `__chat--open` CSS, copied from the already-jitter-
  fixed `.workspace-details__body` block (not the original
  `.project-item-view__chat`, which was the pre-fix version).
- `ProjectItemView.tsx`: now passes `items={allItems}` to `ResearchChatPanel`
  too, so the manual "kick off a run" button works from inside an item's
  chat as well, not just the project-level entry point.
- Renamed the Discovery-only `.discovery-run-card` / `.discovery-kickoff-form`
  CSS classes (and `DiscoveryChatPanel.tsx`'s usages) to `.agent-run-card` /
  `.agent-kickoff-form` — purely structural styling with nothing
  Discovery-specific in it, now shared by both agent chat panels instead of
  research reusing Discovery-prefixed class names.
- Deleted `ResearchKickoffPanel.tsx` — fully superseded, nothing references
  it anymore.

Decisions:
- No ADR — extends the existing chat-agent pattern (ADR 0025) to a second
  entry point rather than introducing new architecture, matching the
  Discovery precedent from earlier today.
- Left `runStatus`/`applyRunEvent`/`activeRunId` in `projectWorkspaceStore.ts`
  as-is per the plan — vestigial now that nothing drives the original
  kickoff connection past its first event, but harmless to leave; not worth
  a cleanup pass in the same change.

Verified: `npm run test` (61 frontend + 224 backend + 10 integration, all
passing — new coverage: `researchChatAgent.test.ts`'s runs-context/system-
turn-stripping test, `projectChatRoute.test.ts`'s new `/research-runs`
endpoint tests, `projectWorkspaceStore.test.ts`'s `upsertChatSession` test,
and a new integration test logging a real bulk run into a real chat session
end-to-end). Both `tsc` checks clean. Did **not** get a live browser
walkthrough this pass — another chat session already owns ports 8787/5173
for its own dev servers, and this session's browser tools can't reach
another session's server; forcing a port switch felt riskier than just
flagging the gap. Automated coverage (unit + the new integration test) is
the verification for this change.
