- **Firestore persistence** (`docs/adr/0018`, supersedes `0016`). New
  `backend/src/services/firestoreClient.ts`. `filmStore.ts` rewritten Firestore-
  backed (`createFirestoreFilmStore`) with an in-memory fake
  (`createInMemoryFilmStore`) for tests, same `FilmStore` interface but every
  method is now `Promise`-returning. New sibling stores follow the identical
  `createFirestore.../createInMemory...` pattern: `detailRowsStore.ts` (rows +
  custom columns, subcollections of `films/{id}`) and `discoveryJobStore.ts`

  queue, claimed FIFO across every film via a `collectionGroup` query).
  `createApp()`'s own default for these stores is now an in-memory fake

  Google-backed service already defaults to a throwing stub. `server.ts`

  create film → prep reaches `ready` → kick off a pass → drive the queue
  worker's `processOne()` directly → stream to `done` → merge a result → confirm
  it landed in `detailRows`. Satisfies the open TODO from the 02:45 entry.
- **Live verification, not just tests**: ran both dev servers for real
  (added a `dev:backend` entry to `.claude/launch.json`, which only had
  `dev:frontend`) against the real Firestore database and walked the full
  happy path in a live browser — import (synthetic File objects injected via
  `DataTransfer`, since this session has no OS file-picker access) → prep
  screen showing all 5 stages transition live → Details table with the
  auto-discovered rows → edited and saved a row → kicked off a named Discovery
  pass → watched it go queued→running→done live → merged a result row →
  **left a comment and kicked the same pass off again**.
  - **First real-infra surprise**: `discoveryJobStore.ts`'s
    `resetStaleRunningJobs` and `claimNextQueuedJob` queries need a Firestore
    composite index that doesn't exist by default — the backend crashed on
    startup with `FAILED_PRECONDITION`. Fixed by adding `.orderBy('createdAt')`
    to `resetStaleRunningJobs` so it reuses the *same* `status+createdAt`
    composite index already declared in `firestore.indexes.json` (one query
    over the collection group needing an unindexed equality filter, once fixed,
    reused the same index cleanly), then created it directly via `gcloud
    firestore indexes composite create` — took effect almost immediately since
    the collection was empty (index *build* time scales with existing data, not
    request latency; the `gcloud` command itself was just slow to return).
  - **Second, real bug in the app itself, caught only by driving it live**:
    the comment-driven re-run got stuck showing "queued" forever in
    `AgentStatusPanel`, even though the backend had actually finished the
    second pass. Root cause: the SSE-subscribe `useEffect` only re-ran on
    `job.id` changing, but a comment re-run reuses the *same* job id — the
    first stream had already closed on its earlier `done` event, so nothing
    ever reconnected. Fixed by also depending on `job?.status`, so a
    `done`→`queued` transition (which *does* change) triggers a resubscribe.
    A **second**, related bug surfaced fixing the first: opening a pass that
    had never been streamed on this page load (e.g. after a reload) got stuck
    on "Loading pass…" forever, because the same effect required `job.id` to
    exist — but `job` itself was what the stream call was supposed to produce.
    Fixed by adding a `jobId: string` prop (always known, from
    `activeJobId`) that the effect depends on directly, decoupling "which job
    to stream" from "has its detail arrived yet." Re-tested both flows live
    after the fix — both now work correctly, log lines from both passes show
    up in order, and reopening a never-streamed pass after a reload loads
    immediately.
  - Also fixed a small polish issue caught live: the auto-discovery-on-create
    rows showed "Agent #0 · Pass #0" (the sentinel provenance from
    `filmPrepPipeline.ts`) — relabeled to "Discovered on import" in
    `DetailsTable.tsx`'s `provenanceLabel`.
  - Cleaned up the manually-created verification film from the real Firestore
    database afterward (`DELETE /api/films/:id`) so it doesn't linger as demo
    clutter.
- Full suite green after the fixes: frontend 49/49 (fewer than the prior
  session's 72 — `NewFilmView.test.tsx`/`FilmDetailView.test.tsx` were deleted
