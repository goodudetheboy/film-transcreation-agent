## Premiere-style zoomable timeline + horizontal transport bar

The user shared a Premiere Pro screenshot as a style reference and asked for the
workspace to feel more like a real NLE, specifically calling out: the timeline
scrubber being unreadable for a long (e.g. 2-hour) film with no way to zoom in, no
time ruler, no numeric time display anywhere, and the transport controls (play/
pause/etc.) sitting in a cramped vertical strip beside the video instead of a
horizontal bar underneath it like Premiere's Program Monitor. Planned this with the
user first (decisions: plain scroll-to-zoom with no modifier key, drop the
redundant "back to films" button from the new bar, fold picture-zoom into the same
bar) before implementing.

- **`frontend/src/components/VideoScrubber.tsx`** — full rewrite. Split the old
  single flat `.scrubber` div into a `.scrubber-viewport` (real `overflow-x: auto`,
  native scrollbar) containing a `.scrubber-track` whose width is `${zoom*100}%`.
  Every existing position (subtitle blocks, fill, playhead) was already expressed
  as a percentage of full duration, so it scales correctly with zoom for free —
  only the container width/scroll position needed new logic. Added:
  - A time ruler with "nice" tick spacing picked from a fixed candidate list
    (100ms…2hr) so labels never overlap regardless of zoom or clip length.
  - Scroll-wheel-to-zoom via a **native** `wheel` listener (`{ passive: false }`)
    attached in `useEffect`, since React 17+ registers `onWheel` passively at the
    root and won't reliably let `preventDefault()` stop page scroll otherwise.
    Zoom is centered on the cursor (classic zoom-to-pointer math).
  - `+`/`−`/Fit buttons next to the timeline for non-scroll access.
- **New `frontend/src/components/TransportBar.tsx`** replaces the deleted
  `VerticalToolbar.tsx`: one horizontal row (skip-back/play-pause/skip-forward,
  a `formatClock(current) / formatClock(duration)` readout, then picture-zoom
  controls) under `.video-stage` instead of beside it —
  `.workspace__panel--video` flipped from `flex-direction: row` to `column` to
  make this the actual layout, per the user's ask.
- `tsc --noEmit` clean, frontend suite 54/54, live-verified in a real browser
  (ticks, zoom-to-cursor, time readout, native panning).

## Follow-up feedback, same session

Three more requests landed while live-verifying the above:

1. **The auto-follow-playhead effect was actively fighting the zoom-to-cursor
   math** — the user zoomed into a region away from the current playhead and

## Video upload: diskStorage instead of memoryStorage

The user is planning to import a real ~20-minute demo film and asked about
bandwidth/memory risk beforehand. `backend/src/routes/films.ts`'s video upload
route used `multer.memoryStorage()`, which buffers the *entire* file into the
Node process's RAM before the handler runs — fine for tiny test clips, a real
risk once real film-length files are involved (each upload spikes backend
memory by the full file size, on a single shared process).

- Switched to `multer.diskStorage()`, with `destination` pointed straight at
  `deps.mockUploadsDir` (created eagerly via `mkdirSync` at router-construction
  time, since diskStorage doesn't auto-create a missing destination the way
  the old lazy `mkdir` call did) and `filename` generating the same
  `${randomUUID()}${guessExtension(...)}` name the handler used to compute
  itself. This turned out to *simplify* the mock-mode branch, not just fix
  it — multer now writes the bytes directly to their final resting place, so
  the old `mkdir`/`writeFile(..., file.buffer)` dance is gone entirely; the
  handler just builds the URL from `file.filename`.
  - The real (bucket) branch still needs an in-memory `Buffer` for
    `videoBucketUploader.uploadBuffer()` — added a `readFile(file.path)` right
    before that call. This doesn't eliminate memory use for that path, but it
    shrinks the window a lot: the potentially-slow, attacker-controllable
    *network receive* no longer holds memory open (that's now a disk write),
    only a fast local disk read does. Didn't touch `videoBucketUploader.ts`
    itself — a true streaming-to-GCS variant exists as a pattern already
    (`uploadFromUrl`'s `createWriteStream` loop) but is more surface area than
    this pass needed, especially since mock mode is what's actually in use.
  - Added `keepFile`-gated cleanup (`rm(file.path, { force: true })` in a
    `finally`) so every path except mock-mode success — content-type
    rejection, real-upload success, real-upload failure — deletes the staged
    temp file instead of leaking it in `mockUploadsDir` forever.
- Live-verified in a real browser: a real upload lands at its final path with
  byte-for-byte the right size, and the film plays back
  (`video.duration`/`readyState` correct, no error); a deliberately-rejected
  non-video upload (`notavideo.txt`) gets its temp file cleaned up rather than
  orphaned. `tsc --noEmit` clean, backend suite 105/105, integration suite's
  one pre-existing unrelated failure (the stale `gs://` assertion, already
  flagged as a background task) is unchanged — the other 3 integration tests
  pass, confirming the upload→serve round trip still works end-to-end.

## Large video uploads: bypass Cloud Run's 32MB body limit

The user tried importing a real ~450MB film and got "Failed to fetch." Diagnosed
live: the exact same file uploaded fine via curl and a real browser `fetch()`
against the *local* backend — ruled out `maxVideoUploadBytes`, multer, basic
connectivity. The user confirmed the real attempt was against the **deployed
Cloud Run** backend. Confirmed via Google's current docs: Cloud Run enforces a
hard, non-configurable **32 MiB limit** on any HTTP/1.1 request carrying a
`Content-Length` header — a video `fetch()`/`FormData` upload always sets that
header, so anything over 32MB gets rejected by Google's front-end proxy before
the app ever sees it, which the browser reports as a bare connection failure.

Planned this with the user (`EnterPlanMode`) before implementing — walked
through the mechanism (resumable-upload sessions vs. signed URLs, chosen for
staying on ADC per `docs/adr/0003` rather than needing a new `signBlob` IAM
grant), then the user asked follow-ups about reliability and a progress bar and
asked to fold in full chunked/resumable uploads rather than a single-shot PUT.

- **Real (non-mock) video uploads now bypass Cloud Run entirely.** New
  `POST /api/films/upload-video/init` (tiny JSON body) mints a GCS
  resumable-upload session (`videoBucketUploader.createResumableUploadSession()`
  in `videoBucketUploader.ts`) and returns its `uploadUrl` plus the eventual
  `gs://` URI. The browser then PUTs the file **directly to
  storage.googleapis.com** in 8MiB chunks
  (new `frontend/src/api/resumableUpload.ts`, implementing Google's documented
  resumable-upload protocol by hand — no new dependency). A failed chunk
  triggers a status-check request (asks GCS how many bytes it actually has)
  and resumes from that offset rather than restarting, up to 3 attempts per
  chunk with backoff. `ImportFilmModal.tsx` shows upload progress via a
  `<progress>` bar driven by chunk-completion callbacks.
- **Mock mode is unchanged** — still posts through the existing multer/
  diskStorage route, by design (small test clips only, not real films; scope
  decision made with the user before implementing).
- Bumped `MAX_VIDEO_UPLOAD_BYTES` default 500MB → 2GB (`config/env.ts`) —
  matches the code's own pre-existing comment about real films running
  "hundreds of MB to a few GB."
- Also fixed the pre-existing stale `expect(videoUrl).toMatch(/^gs:\/\//)`
  assertion in `films.integration.test.ts` (flagged in `20260829.md`) while
  touching that file — mock mode actually returns an
  `http://.../mock-uploads/...` URL, not `gs://`.
- New ADR: `docs/adr/0024-direct-to-gcs-video-uploads.md`. New runbook step in
  `docs/runbook.md`: the video bucket needs a one-time CORS policy (`PUT` from
  the frontend's origins) since the browser now talks to
  `storage.googleapis.com` directly — kept as a manual step per the precedent
  `0011` already set for IAM grants, not scripted into `scripts/deploy.sh`.

**Verification**: `npm run test:backend`/`test:frontend`/`test:integration` all
green (113/61/5 tests — new coverage for `createResumableUploadSession`, the
`init` route, `resumableUpload.ts`'s chunk/retry/resume logic, and a new
integration test that drives the real chunk protocol over real TCP against a
fake-GCS stub server in-test). `tsc --noEmit` clean on both packages.

Live-verified against the **real** bucket, not just fakes: ran the CORS setup
step (with the user's explicit go-ahead, since it's a real infra change) and
uploaded the actual 450MB file. Ran a direct Node-based test of the same chunk
protocol against the real resumable session and it completed cleanly (all 54
chunks, byte-perfect, clean final response) — **wrongly** taken at the time as
proof the browser-side fix worked. It wasn't: Node's `fetch` doesn't send an
`Origin` header, so that test couldn't have hit a CORS problem even if one
existed, and one did (see below). Deleted the four ~429MB test objects this
session created from the real bucket afterward.

**Correction, same session**: shipped the fix to `main` (commit `025baba`),
then the user tried it for real in their own Chrome and hit "Failed to fetch"
again — this time with visible DevTools console output showing a genuine CORS
error against `storage.googleapis.com`, not a sandboxed-pane artifact as
earlier (wrongly) concluded above. Reproduced deterministically with per-chunk
logging in a real browser: **every intermediate `308 Resume Incomplete`
response from GCS carries a correct `Access-Control-Allow-Origin` header; the
completing `200` response never does** — confirmed directly with `curl`
(manually setting `Origin`, bypassing browser enforcement, purely to inspect
what GCS actually sends back). This is a genuine, apparently-undocumented GCS
platform behavior: a browser's `fetch()` can never read confirmation of a
resumable upload's own completion, success or failure, since the response
that would confirm it structurally omits the header a browser requires to read
it. See `docs/adr/0024`'s "Update" section for the full writeup.

Fix: `resumableUpload.ts` now treats a thrown error on the *final* chunk as
expected (not fatal) and resolves anyway — the bytes are sent regardless of
whether the response was readable. A new backend route,
`POST /api/films/upload-video/finalize`, independently confirms completion via
GCS object metadata (unaffected by browser CORS, since it's server-to-server)
and `filmsApiClient.uploadVideoFile` calls it after the resumable upload
returns. This same route also closes the size-cap gap flagged earlier in
conversation (a client could previously lie about the size it declares at
`/init` time, since GCS doesn't itself enforce a resumable session's total
against what was declared at creation) — `/finalize` checks the *actual*
uploaded size and deletes the object if it's over `maxVideoUploadBytes`.

Re-verified against the real bucket end-to-end via the actual browser
`uploadVideoFile()` call this time (not Node) — full progress to 100%, clean
`{ videoUrl }` result returned to the client, object confirmed byte-perfect
(449,236,799 bytes) via an independent `gcloud storage ls -l`. All three test
suites green again after updating `resumableUpload.test.ts` (the final-chunk
retry tests had to be rewritten around the new expected-throw-resolves
behavior) and adding coverage for the new route, `getObjectSizeBytes`,
`deleteObject`, and a new integration test that reproduces the exact
dropped-completion-response scenario against a fake server. `tsc --noEmit`
clean on both packages. Pushed the corrected fix to `main`.

## DetailsTable: edit modal, height overflow, and a column-resize bug

Three requests from the user after seeing the real film's 126-row Details
table for the first time (`DetailsTable.tsx`, `index.css`):

1. **Row click → modal, not inline-editable row.** Removed all the inline
   `isEditing ? <input> : text` branching in table cells; a row click now opens
   a `.modal-backdrop`/`.modal` dialog (same pattern as `ImportFilmModal`/
   `AgentKickoffPanel`) showing every field at full size — textareas for
   segment description/gesture/notes/custom columns instead of single-line
   inputs, since the whole point was viewing long AI-generated text in full.
   Added Escape-to-close, matching baseline modal expectations even though not
   explicitly asked. `handleDelete` now also closes the modal if the row being
   deleted is the one currently open in it (would otherwise crash on
   `rows.find(...)!` returning undefined).
2. **Table overflow pushing the horizontal scrollbar far down.** First pass
   capped `.details-table-scroll` at a flat `max-height: 60vh` — measured
   live and found this was actually *taller than the panel itself* (529px
   table vs. 488px panel), so the user immediately reported still having to
   scroll (now the panel, not the page) to reach the scrollbar. Real fix:
   `.details-table-wrap`/`.details-table-scroll` are now `flex: 1; min-height:
   0` inside `.workspace__panel--left`'s existing flex column, so the table
   area fills exactly whatever space is actually left after the heading and
   the two button rows below it — measured after the fix: panel
   `scrollHeight === clientHeight` (was 750 vs 488), i.e. the panel needs zero
   scroll now regardless of row count. Also made `.details-table th`
   `position: sticky` so the column headers stay visible while scrolling
   within the now-bounded table area.
3. **Column-resize drag "stuck" unless dragging very slowly.** Root cause:
   `ResizableTh` was defined *inside* `DetailsTable`'s render body — a new
   function/component identity on every render, so every `setColWidths`
   during a drag made React tear down and recreate the actual `<span>` DOM
   node, silently losing the `setPointerCapture()` that was supposed to keep
   tracking the cursor. Moved `ResizableTh` to module scope (handlers passed
   as props instead of closed over) so the DOM node — and its pointer capture
   — survives re-renders. Verified by dispatching real `PointerEvent`s
   directly (both one big fast jump and a smooth 10-step drag) and confirming
   the resulting column width matched the delta exactly in both cases; before
   the fix this class of bug wouldn't have worked for a fast drag.

Live-verified all three against the real 126-row "Disney's Inside Out" film:
opened the modal, edited and saved a field (round-tripped through the real
backend, then reverted the test edit afterward), scrolled the bounded table
with the header staying pinned, and confirmed the fast/multi-step drag
scenarios both land the resizer exactly where the cursor stopped.
`tsc --noEmit` and the full frontend suite (63/63) stayed clean throughout — no
existing `DetailsTable` test file existed to update (pre-existing gap, still
open, see TODOs).
