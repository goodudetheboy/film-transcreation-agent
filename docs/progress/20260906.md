## 14:15 — Fixed real bugs the user caught live, plus one major root-cause find

User watched the six Lottie scenes live and reported real problems, several of
which turned out to share one root cause. All fixed by regenerating the JSON
assets in `frontend/src/assets/animations/` (no `.tsx`/`.css` changes this
round) — see [[feedback-lottie-web-authoring]] for the durable technical
writeup, kept there since the next session doing Lottie work needs it, not
just this one.

**The big one — every layer went `display:none` after frame 90, always.**
`lottie-helpers.mjs`'s `shapeLayer()` defaulted a layer's own `op` (out-point)
to 90 whenever a call site didn't pass one explicitly, and *no* call site in
`preparing` (120-frame loop), `finalizing` (180-frame loop), or `discovery`
(130-frame loop) passed one. Every layer in those three scenes silently went
invisible for the entire tail of each loop before snapping back at the
restart — this was "the spinner isn't spinning" (it kept rotating, just
behind an invisible layer) and "everything disappears for a split second
before repeating." Fixed once, structurally, in `scene()`: it now forces
every layer's `ip`/`op` to the scene's own values, so a per-layer omission
can't reintroduce this.

**The second one — omitting an "unnecessary" keyframe handle corrupts
lottie-web.** The discovery magnifier's position animation used a ternary to
skip the incoming handle on keyframe 0 and the outgoing handle on the last
keyframe (reasonable-looking; there's no adjacent segment for either to
affect). It rendered as a `matrix(...,-999999,-999999)` transform — a
garbage sentinel, not a real interpolated value — while Skottie had rendered
it fine. Took an extended isolation pass (stripped rotation, shape count,
anchor value, easing curve, cloned the shared easing-anchor objects, moved
the layer's array position, renamed it) before landing on the actual
variable: whether *both* handles were present on every keyframe. Fixed in
`kf()`: it now always attaches both handles, defaulting to a new
near-linear `LINEAR_O`/`LINEAR_I` pair when a call site passes neither,
rather than ever leaving one `undefined`.

**That fix's own side effect — a "hold" expressed as two identical-value
keyframes is the same zero-magnitude-segment bug from `ready`'s box layer
earlier today, just reintroduced.** Once `kf()` started always attaching
handles, every place a deliberate hold had been written as two adjacent
keyframes sharing one value (`finalizing`'s pack-icon opacity/position,
`preparing`'s clapper rotation settle, the upload icon's opacity, the
record-dot blink, all three script-line trim draws) got real handles on a
zero-delta segment for the first time and broke the same way. This is what
"the video and subtitle are flying to the wrong part" and "pulled to the
left" actually were — not a positioning-math error, the pack-icon layer's
own transform was corrupted the same `-999999` way once its `p` array's
redundant `kf(113, [dx,78,0])` (identical to the prior keyframe) got real
handles. Fixed by deleting every redundant same-value keyframe rather than
special-casing handles again — a property already holds its last keyframe's
value once fired, so the "hold" needs no second keyframe at all. Wrote
`scripts/check-zero-delta.mjs` (a throwaway checker, not committed) to
grep every generated scene's keyframe arrays for adjacent-same-value pairs
automatically instead of relying on manual review — it caught 7 more
instances across `preparing`/`video-uploading`/`subtitle-uploading` in one
pass once pointed at the regenerated files.

**Smaller content fixes**, all per direct user feedback: `discovery`'s
sparkle stars had the exact same "renders at (0,0) instead of its real
position" bug as the ready-scene lesson already in memory (anchor equalled
position with the shape authored at local origin — net-zero offset lands it
at absolute (0,0), not the intended point); fixed by setting `anchor:[0,0]`
and putting the real position on the layer's `p` instead. Sparkle shape
swapped from a generic 4-point polystar back to the exact original 8-point
star path from `PrepAnimation.tsx`'s `.prep-sparkle` CSS, per "the sparkly
star should be the same as the old one." Upload scene's arrow removed
entirely and the icon's tail motion changed from "slide back down while
fading" to "fade out in place" (the sliding was what read as reversed
direction) — extended into "rise up all the way to visually touch the
cloud's underside" per follow-up feedback, instead of stopping short at a
mid-canvas rest position.

Verified: regenerated all 6 scenes, ran the zero-delta checker clean, spot-
checked each live via `/dev/prep-animation` (screenshots plus serialized-SVG
inspection — false-positive note: a naive substring search for "999999" also
matches ordinary float rounding like `91.19999694824219`, so the real check
needs to parse transform matrices and flag actual out-of-range magnitudes,
not just grep the string). `npx tsc -p tsconfig.app.json --noEmit`,
`npx oxlint .`, `npx vitest run` (66/66) all clean. User confirmed live and
asked to ship straight to `main` again.

**Root cause**, found via an Explore agent then confirmed by reading the code:
[discoveryChatAgent.ts](../../backend/src/services/discoveryChatAgent.ts)'s
`runTurn` looped over a model turn's `functionCall` parts and persisted **one
separate `role:'user'` turn per call**, each with a single `functionResponse`
part, instead of bundling all of a round's responses into one turn — which is
what the Gemini API actually requires when the model returns multiple parallel
function calls in one turn. Worse, a `signal?.aborted` check *inside* that
per-call loop could `break` before every call in the round got a response,
permanently corrupting that session's persisted history (every future turn
would resend the mismatched call/response counts and hit the same 400 again).
The identical pattern existed in
[researchChatAgent.ts](../../backend/src/services/researchChatAgent.ts)'s
`runTurn` — same fix applied there too, even though no live report came in for
it yet.

Fix: collect all of a round's `functionResponse` parts into one array, execute
every pending tool call to completion first, then push a single bundled
`{ role: 'user', parts: responseParts }` turn — only checking `signal.aborted`
*after* the round finishes (before deciding whether to start another round),
never mid-round. New regression test in
[discoveryChatAgent.test.ts](../../backend/src/services/discoveryChatAgent.test.ts)
sends two parallel `functionCall` parts in one mocked model turn and asserts
the persisted history is exactly `['user','model','user','model']` (one
bundled response turn, not two).

**Also added, per user request in the same conversation:** the Discovery chat
agent can now add and delete whole Detail rows, not just edit fields or
accept/discard candidates. New `add_detail_row`
(startMs/endMs + optional segmentDescription/gesture/notes; subtitle text is
derived the same way `POST /api/films/:id/details` already does, via
`subtitleTextForRange`) and `delete_detail_row` (rowId) tool declarations in
`CHAT_TOOLS`, both wired into `executeTool` and reusing the same
`detailRowsStore.addRow`/`deleteRow` the REST routes call. Needed threading a
`filmStore` dependency into `DiscoveryChatAgentDeps`/`ExecuteToolDeps` (to look
up the film's subtitle entries for the new row) — updated `app.ts`, `server.ts`,
`mockDiscoveryChatAgent.ts`, and the test file's `buildDeps()` accordingly. Two
new stream event types, `row_created`/`row_deleted`, alongside the existing
`row_patched`/`row_added`/`row_discarded`; wired into
[filmWorkspaceStore.ts](../../frontend/src/store/filmWorkspaceStore.ts)'s
`applyDiscoveryChatEvent` (`row_created`/`row_added` both call `addRow`,
`row_deleted` calls the already-existing `removeRow`) and given chat-log labels
in [DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx)'s
`DiscoveryToolCallCard`. Did not extend `mockDiscoveryChatAgent.ts`'s scripted
demo to showcase the new tools — it's a fixed canned script (merge-or-edit),
not a general tool-calling loop, so there's nothing to wire there.

Decisions:
- No new ADR — additive tool/bugfix within the existing Discovery Agent chat
  design, not an architectural change.
- New rows created via chat use `provenance: { type: 'user-marked' }`, same as
  the REST add-row endpoint — the `ai-assisted`/`agent-discovered` provenance
  variants require a `jobId`/`passNumber` that a direct chat-tool add doesn't
  have.
- Left the already-corrupted in-memory session from before this fix alone (no
  repair path added) — sessions are in-memory/test-mode data here, so a server
  restart clears it; adding history-repair logic for a state that shouldn't be
  reachable anymore would be unjustified scope.

Verified: `npm run test` — 249 backend (4 new: `add_detail_row` happy path +
invalid-range rejection, `delete_detail_row`, the parallel-tool-call bundling
regression test), 66 frontend, 11 integration, all passing. Both `tsc -b`
checks (backend and frontend) and `oxlint .` clean (only pre-existing,
unrelated warnings elsewhere in the repo). Not live-walked through the actual
Gemini-backed chat in the browser — that needs real ADC credentials and a live
