## 12:15 — Phase 5: sequenced the upload-flow animations (3s floor)

Root cause (plan-mode research, not guessed): `PrepAnimation.tsx` has 5
animated scenes — `video_uploading`, `subtitle_uploading`, `discovery_running`,
`finalizing`, `ready` — sequenced by `FilmPreparingView.tsx` via the
already-correct dwell-queue hook `useStageDwell.ts` (built 2026-09-02). But
`video_uploading`/`subtitle_uploading` were never reachable: the backend's
`initialPrep()` (`backend/src/services/filmStore.ts`) starts a film's
`prep.stage` directly at `discovery_running`/`finalizing`, because the real
video/subtitle uploads happen earlier in
[ImportFilmPage.tsx](../../frontend/src/views/ImportFilmPage.tsx), before
`createFilm` is ever called. So `FilmPreparingView` always opened on index 2 of
its 5-stage order — "stage 3 of 5" — and the two upload animations were dead
code. Frontend-only fix, no backend change, no new ADR (additive UI fix, same
category as Phase 4).

User asked for a 3s minimum dwell, not the 5s originally written when this was
triaged 2026-09-05.

Changes:
- New [withMinDuration.ts](../../frontend/src/utils/withMinDuration.ts) —
  `withMinDuration(work, minMs, sleepImpl?)`, floor-not-ceiling via
  `Promise.all([work, sleepImpl(minMs)])`, rejects immediately on `work`
  rejection without waiting out the floor. Follows the `sleepImpl`-injection
  convention already established in `resumableUpload.ts` rather than reusing
  `StageDwellController` (that class exists to drain a burst of externally
  pushed SSE events — the wrong tool for a call site that fully controls its
  own two-step sequence).
- [useStageDwell.ts](../../frontend/src/utils/useStageDwell.ts): added
  `export const MIN_STAGE_DWELL_MS = 3000` and made it the hook's default
  (was a bare `2000` literal), so "3 seconds" is one constant shared with
  `ImportFilmPage.tsx` instead of two independent numbers.
- [ImportFilmPage.tsx](../../frontend/src/views/ImportFilmPage.tsx):
  `handleSubmit` now sets an `animationStage` (`'video_uploading' |
  'subtitle_uploading' | null`) alongside the existing `status` text, and
  wraps the `uploadVideoFile`/`uploadSubtitleFile` calls in `withMinDuration`.
  The `import-columns` block conditionally swaps the two drop-zone columns for
  `<PrepAnimation stage={animationStage} />` (video stage keeps the real
  `<progress>` bar right under it, moved from the footer). Deliberately did
  *not* add a third animated stage for the `createFilm()` call — an earlier
  draft considered reusing the `finalizing` scene there for continuity, but
  rejected it: if discovery is enabled the backend's very next real stage is
  `discovery_running`, not `finalizing`, so "wrapping up" before discovery
  even starts would be actively misleading, and it's unnecessary anyway since
  `useStageDwell` already opens every `FilmPreparingView` mount on its own
  `'preparing'` idle animation before the first real stage renders. The
  `catch` block now also resets `animationStage`/`uploadProgress` so a failed
  upload cleanly returns to the editable form.
- No CSS changes needed — `.prep-scene` is self-contained and
  `.import-columns__col` already centers its children correctly.

New tests (none existed for any of this before):
[withMinDuration.test.ts](../../frontend/src/utils/__tests__/withMinDuration.test.ts)
(floor timing, no-extra-wait-past-floor, fail-fast on rejection) and

User caught real problems on the first pass, each fixed before moving on:
- Finalizing's lid started closing while the packed icons were still

- The gift box (both closing in `finalizing` and already-open in `ready`)

- Cloud-upload scene had an arrow icon and read as going the wrong
  direction — removed the arrowhead entirely, and found the real cause of
  the "reversed" feel: the file icon was sliding back down as it faded out
  before each loop restart. Fixed by having it fade out fully in place

  since opacity is 0 across the whole loop seam).
- The cloud shape itself (three overlapping ellipses) looked "scuffed" —
  replaced with a proper flat-bottom cloud-storage silhouette (the same
  family every SaaS upload icon uses), derived by scaling Material
  Design's 24x24 cloud glyph path up to this canvas and converting it to

Three real lottie-web-specific bugs surfaced via live testing (not caught by
the Skottie sandbox, which is more lenient) — each is now a documented rule
in the throwaway generator scripts (`scratchpad/lottie-lab/scripts/`) and in
the commit message:
1. A redundant same-value keyframe pair with custom eased handles (used to
   emulate a CSS `animation-delay`) blows up lottie-web's SVG interpolator
   into a `-9999` scale, rendering as a solid color filling the whole
   canvas. Fix: never author a hold as two identical-value keyframes with
   easing handles — a property already holds its first keyframe's value
   for any time before it.
2. A shape animated as a *sibling* top-level layer (e.g. a "recording" dot
   meant to ride along on the video icon, or a document's text lines) has
   static absolute coordinates and doesn't inherit the icon's own rise/fall
   motion — it floats disconnected. Fix: nest it as a sub-group inside the
   icon layer's own `shapes` array instead, so it inherits that layer's
   transform for free (per-group opacity/trim still works independently
   inside the nested group).
3. Lottie's polystar shape (`ty: 'sr'`) needs an explicit `sy` (star vs.
   polygon) field — omitting it didn't just break that one sparkle, it
   silently rendered the *entire* discovery scene as an empty `<g>` in
   lottie-web (structural check on the serialized SVG's byte length caught
   this immediately; Skottie had rendered it fine).

`PrepAnimation.tsx` collapsed to a thin switch over `LottiePlayer` instances
(`Glow`, `PreparingScene`, `UploadScene`, `DiscoveryScene`, `PackingScene`'s
old SVG bodies, and `PARTICLE_DELAYS`, all deleted); all the corresponding
hand-coded SVG/CSS keyframe rules deleted from `index.css` (grepped

unreferenced, same as the `ready`-scene cleanup earlier today).

## 14:15 — Fixed real bugs the user caught live, plus one major root-cause find

User watched the six Lottie scenes live and reported real problems, several of
which turned out to share one root cause. All fixed by regenerating the JSON
assets in `frontend/src/assets/animations/` (no `.tsx`/`.css` changes this
round) — see [[feedback-lottie-web-authoring]] for the durable technical
writeup, kept there since the next session doing Lottie work needs it, not
just this one.

**The big one — every layer went `display:none` after frame 90, always.**
`lottie-helpers.mjs`'s `shapeLayer()` defaulted a layer's own `op` (out-point)
to 90 whenever a call site didn't pass one explicitly, and *no* call site in
`preparing` (120-frame loop), `finalizing` (180-frame loop), or `discovery`
(130-frame loop) passed one. Every layer in those three scenes silently went
invisible for the entire tail of each loop before snapping back at the
restart — this was "the spinner isn't spinning" (it kept rotating, just
behind an invisible layer) and "everything disappears for a split second
before repeating." Fixed once, structurally, in `scene()`: it now forces
every layer's `ip`/`op` to the scene's own values, so a per-layer omission
can't reintroduce this.

**The second one — omitting an "unnecessary" keyframe handle corrupts
lottie-web.** The discovery magnifier's position animation used a ternary to
skip the incoming handle on keyframe 0 and the outgoing handle on the last
keyframe (reasonable-looking; there's no adjacent segment for either to
affect). It rendered as a `matrix(...,-999999,-999999)` transform — a
garbage sentinel, not a real interpolated value — while Skottie had rendered
it fine. Took an extended isolation pass (stripped rotation, shape count,
anchor value, easing curve, cloned the shared easing-anchor objects, moved
the layer's array position, renamed it) before landing on the actual
variable: whether *both* handles were present on every keyframe. Fixed in
`kf()`: it now always attaches both handles, defaulting to a new
near-linear `LINEAR_O`/`LINEAR_I` pair when a call site passes neither,
rather than ever leaving one `undefined`.

**That fix's own side effect — a "hold" expressed as two identical-value
keyframes is the same zero-magnitude-segment bug from `ready`'s box layer
earlier today, just reintroduced.** Once `kf()` started always attaching
handles, every place a deliberate hold had been written as two adjacent
keyframes sharing one value (`finalizing`'s pack-icon opacity/position,
`preparing`'s clapper rotation settle, the upload icon's opacity, the
record-dot blink, all three script-line trim draws) got real handles on a
zero-delta segment for the first time and broke the same way. This is what
"the video and subtitle are flying to the wrong part" and "pulled to the
left" actually were — not a positioning-math error, the pack-icon layer's
own transform was corrupted the same `-999999` way once its `p` array's
redundant `kf(113, [dx,78,0])` (identical to the prior keyframe) got real
handles. Fixed by deleting every redundant same-value keyframe rather than
special-casing handles again — a property already holds its last keyframe's
value once fired, so the "hold" needs no second keyframe at all. Wrote
`scripts/check-zero-delta.mjs` (a throwaway checker, not committed) to
grep every generated scene's keyframe arrays for adjacent-same-value pairs
automatically instead of relying on manual review — it caught 7 more
instances across `preparing`/`video-uploading`/`subtitle-uploading` in one
pass once pointed at the regenerated files.

**Smaller content fixes**, all per direct user feedback: `discovery`'s
sparkle stars had the exact same "renders at (0,0) instead of its real
position" bug as the ready-scene lesson already in memory (anchor equalled
position with the shape authored at local origin — net-zero offset lands it
at absolute (0,0), not the intended point); fixed by setting `anchor:[0,0]`
and putting the real position on the layer's `p` instead. Sparkle shape
swapped from a generic 4-point polystar back to the exact original 8-point
star path from `PrepAnimation.tsx`'s `.prep-sparkle` CSS, per "the sparkly
star should be the same as the old one." Upload scene's arrow removed
entirely and the icon's tail motion changed from "slide back down while
fading" to "fade out in place" (the sliding was what read as reversed
direction) — extended into "rise up all the way to visually touch the
cloud's underside" per follow-up feedback, instead of stopping short at a
mid-canvas rest position.

Verified: regenerated all 6 scenes, ran the zero-delta checker clean, spot-
checked each live via `/dev/prep-animation` (screenshots plus serialized-SVG
inspection — false-positive note: a naive substring search for "999999" also
matches ordinary float rounding like `91.19999694824219`, so the real check
needs to parse transform matrices and flag actual out-of-range magnitudes,
not just grep the string). `npx tsc -p tsconfig.app.json --noEmit`,
`npx oxlint .`, `npx vitest run` (66/66) all clean. User confirmed live and
asked to ship straight to `main` again.
