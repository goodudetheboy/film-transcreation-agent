## 00:35 — Fixed a scuffed DiscoveryResultsModal layout

User caught this live (screenshot) right after the Phase 4 entry above: the
results-modal table was cramped into the 480px `kickoff-modal` width with no
`<colgroup>`, so `table-layout: fixed` (the same rule the main Details table relies
on) divided that narrow space evenly across every column — the "Add" button
rendered as an oversized block and the trash-icon button got clipped to a sliver.
First tried collapsing the table to 3 columns with a "click a row to inspect in a
modal" flow; user reversed that — wanted the full column set, styled exactly like
the real Details table (resizable columns, its own horizontal scrollbar), just in a
wider modal.

Extracted the two pieces `DetailsTable.tsx`'s column-resize drag behavior was built
from — the `ResizableTh` component and the pointer-drag state/handlers — into
shared [ResizableTh.tsx](../../frontend/src/components/ResizableTh.tsx) and
[useResizableColumns.ts](../../frontend/src/utils/useResizableColumns.ts), then
refactored `DetailsTable.tsx` to use them (behavior unchanged, verbatim logic) so
[DiscoveryChatPanel.tsx](../../frontend/src/components/DiscoveryChatPanel.tsx)'s
`DiscoveryResultsModal` could reuse the exact same mechanism instead of
reinventing it. The modal's table now has a real `<colgroup>` with the same
per-column defaults as `DetailsTable.tsx` (Start/End/Subtitle/Segment
Description/Gesture/Notes/custom columns, checkbox and actions columns fixed but
not resizable — same as the main table's own non-resizable actions column), and a
new `.discovery-results-modal` CSS class (`width: 90vw; max-width: 1200px`) gives
it room; `.details-table-wrap--standalone` (already used for exactly this
"table dropped into a modal" case elsewhere in this app) handles the internal
vertical scroll.

## 12:15 — Phase 5: sequenced the upload-flow animations (3s floor)

Root cause (plan-mode research, not guessed): `PrepAnimation.tsx` has 5
animated scenes — `video_uploading`, `subtitle_uploading`, `discovery_running`,
`finalizing`, `ready` — sequenced by `FilmPreparingView.tsx` via the
already-correct dwell-queue hook `useStageDwell.ts` (built 2026-09-02). But
`video_uploading`/`subtitle_uploading` were never reachable: the backend's
`initialPrep()` (`backend/src/services/filmStore.ts`) starts a film's
`prep.stage` directly at `discovery_running`/`finalizing`, because the real
video/subtitle uploads happen earlier in
[ImportFilmPage.tsx](../../frontend/src/views/ImportFilmPage.tsx), before
`createFilm` is ever called. So `FilmPreparingView` always opened on index 2 of
its 5-stage order — "stage 3 of 5" — and the two upload animations were dead
code. Frontend-only fix, no backend change, no new ADR (additive UI fix, same
category as Phase 4).

User asked for a 3s minimum dwell, not the 5s originally written when this was
triaged 2026-09-05.

Changes:
- New [withMinDuration.ts](../../frontend/src/utils/withMinDuration.ts) —
  `withMinDuration(work, minMs, sleepImpl?)`, floor-not-ceiling via
  `Promise.all([work, sleepImpl(minMs)])`, rejects immediately on `work`
  rejection without waiting out the floor. Follows the `sleepImpl`-injection
  convention already established in `resumableUpload.ts` rather than reusing
  `StageDwellController` (that class exists to drain a burst of externally
  pushed SSE events — the wrong tool for a call site that fully controls its
  own two-step sequence).
- [useStageDwell.ts](../../frontend/src/utils/useStageDwell.ts): added
  `export const MIN_STAGE_DWELL_MS = 3000` and made it the hook's default
  (was a bare `2000` literal), so "3 seconds" is one constant shared with
  `ImportFilmPage.tsx` instead of two independent numbers.
- [ImportFilmPage.tsx](../../frontend/src/views/ImportFilmPage.tsx):
  `handleSubmit` now sets an `animationStage` (`'video_uploading' |
  'subtitle_uploading' | null`) alongside the existing `status` text, and
  wraps the `uploadVideoFile`/`uploadSubtitleFile` calls in `withMinDuration`.
  The `import-columns` block conditionally swaps the two drop-zone columns for
  `<PrepAnimation stage={animationStage} />` (video stage keeps the real
  `<progress>` bar right under it, moved from the footer). Deliberately did
  *not* add a third animated stage for the `createFilm()` call — an earlier
  draft considered reusing the `finalizing` scene there for continuity, but
  rejected it: if discovery is enabled the backend's very next real stage is
  `discovery_running`, not `finalizing`, so "wrapping up" before discovery
  even starts would be actively misleading, and it's unnecessary anyway since
  `useStageDwell` already opens every `FilmPreparingView` mount on its own
  `'preparing'` idle animation before the first real stage renders. The
  `catch` block now also resets `animationStage`/`uploadProgress` so a failed
  upload cleanly returns to the editable form.
- No CSS changes needed — `.prep-scene` is self-contained and
  `.import-columns__col` already centers its children correctly.

New tests (none existed for any of this before):
[withMinDuration.test.ts](../../frontend/src/utils/__tests__/withMinDuration.test.ts)
(floor timing, no-extra-wait-past-floor, fail-fast on rejection) and
[ImportFilmPage.test.tsx](../../frontend/src/views/ImportFilmPage.test.tsx)
(full video→subtitle→create→navigate sequencing under `vi.useFakeTimers()` +
`vi.advanceTimersByTimeAsync`, wrapped in `act()` — needed because React 18's
scheduler doesn't flush through fake-timer advancement on its own; and a
fail-fast-on-upload-error test). `npm run test:frontend`: 66/66 passing (up
from 61). `tsc -p tsconfig.app.json` and `oxlint` clean.

Live-walked via the dev servers (Browser pane, test mode): submitted the

Confirmed the full run through to `ready` and an enabled "Start Creating".
Test film deleted afterward.
